# New-repository Sprint 2: staff identity and scoped authorization

Status: engineering implementation in progress, 16 September 2026. Scope: South Africa only. This re-baselines E04 and the relevant security work for the clean solution; it does **not** revive the old repository's S2 route-audit, credential or migration tasks. A completed engineering sprint is not production authorization. Product, Church and security owners must approve the decisions and release evidence below.

Engineering progress: the account store, invitation primitive, dated-grant persistence/readers, scoped evaluator, sign-in form, sign-out action and first protected branch-read API are implemented. Accounts start inactive; an internal, single-use invitation service binds an expiring token to an email destination and enrolls a password on redemption. There is no public invitation issuance, redemption, registration, recovery or grant-administration route, and no email/SMS delivery. The Web host requires authentication by default, rechecks account state/security stamp on each signed-cookie request, and authorizes a branch using its loaded `ChurchId` and organization ancestry. Unknown and unauthorized branch IDs return the same 403 without branch data. Tests use synthetic identities and grants, including HTTP-level denial and same-session revocation. Release build and all 68 tests pass. All five Organization, Identity and Authorization migrations were reviewed and applied in order to the newly named, isolated local validation database `TheChg_Sprint2Integrated_20260916_F3B86C`; a read-only SQL check found the expected cross-schema foreign keys and zero Churches, users, invitations or grants. All three EF contexts report no pending model changes. The earlier baseline was separately validated in `TheChg_Sprint2Validation_20260916_A7C9F2`. The plan below still contains policy and release gates, not a claim that a staff pilot is approved.

The account `ChurchId` foreign key, same-Church grant/unit foreign keys and HTTP-level denial/revocation tests have been implemented and validated in isolation. Framework Identity role tables exist for storage compatibility but **do not themselves grant scoped Church permissions**. No route may rely on authentication alone for resource access. Real-cookie, end-to-end sign-in-to-branch testing remains open; the HTTP security harness uses synthetic authentication.

## Outcome and boundary

Establish a distinct staff account model and a default-deny server-side authorization boundary for the existing denomination → South Africa → circuit → branch tree. An authenticated staff user receives access only through an active, dated assignment, an explicit permission and a matching organizational scope. The first permitted vertical slice is a **read-only, staff-only organization view**; organization writes remain closed until grant administration, audit and policy approval are complete. The Sprint 1 migration and organization tests remain the baseline.

Use ASP.NET Core Identity for credentials as proposed in [ADR 0003](../adr/0003-identity-and-scoped-authorization.md), with `ApplicationUser` separate from future `Member` and `MemberUserLink`. Do not create official membership through account creation. `ChurchId` is server-resolved; client-supplied church or organization IDs are lookup targets, never authority. The [permission matrix](../architecture/permissions-matrix.md) remains a draft design until Church/security approval.

## Execution sequence and acceptance evidence

| Step | Required evidence |
|---|---|
| 1. Contract and policy review | Security lead, product owner and Church representative review proposed permissions, scope inheritance, privileged roles, invitation eligibility, account disablement and the initial role templates. Record unresolved choices below; tests may use synthetic grants without treating templates as approved policy. |
| 2. Persistence foundation | Migration is reviewed before application to an isolated empty development/test database. Unique and foreign-key constraints prevent duplicate assignments, invalid units, cross-Church references and invalid effective ranges where feasible; domain/application checks cover remaining invariants. No production migration or data import. |
| 3. Core authorization | A branch grant allows only that branch; a circuit grant includes descendants **only if** the assignment explicitly says so; country and denomination scopes obey the same rule. Grant creation may not exceed the grantor's effective permissions and scope. Denial is the default for missing, expired, revoked, disabled or ambiguous authority. |
| 4. Authentication and session handling | Password and token flows use framework controls, lockout, secure/HttpOnly/SameSite cookies and antiforgery for browser state changes. Privileged MFA and a measured revocation window are implemented before privileged administration is enabled. No hard-coded credentials, secrets or real people in fixtures. |
| 5. Thin vertical slice | A synthetic, scoped staff account signs in and reads an allowed branch's organization details. The same account cannot read a sibling branch by replacing an ID; anonymous access is denied; unauthorized API and UI paths return no restricted data. No organization mutation endpoint is enabled. |
| 6. Integrated verification | Restore, Release build, all tests, architecture checks and secret/dependency scans pass in CI. Independent security review inspects the policy application on every exposed route and the migration. Evidence links are captured in the sprint review. |

Minimum negative tests (use synthetic data, at least two circuits and sibling branches): anonymous request; authenticated account without a grant; expired/not-yet-active/revoked assignment; disabled account; sibling branch read; circuit without descendant flag reading a child; circuit with descendant flag reading outside circuit; cross-`ChurchId` target; guessed resource ID; stale session after revocation; duplicate/replayed or expired invitation; invalid/forged login and recovery tokens; staff attempting to grant a wider scope or permission; unsafe POST without antiforgery; authorization failure not leaking record existence or fields. For privileged operations, verify MFA is enforced and removal of access is audited. Cross-check the full [test strategy](test-strategy.md) and [threat model](../security/threat-model.md).

## Release gates and decisions

| Gate / owner | Pass condition; otherwise |
|---|---|
| Engineering merge — technical lead and QA | A–D integrate without circular references, migration is reviewed, all CI checks pass and no write route is accidentally exposed. Otherwise keep the feature branch or route disabled. |
| Security acceptance — security lead | Denial matrix, session revocation, privileged MFA, audit and invitation tests pass; no critical/high finding remains unowned. Otherwise no staff pilot. |
| Church policy — Church leadership and product owner | Approve who may receive staff access, initial role/permission templates, scope inheritance and invitation authority. Draft matrix alone is not approval. Otherwise use synthetic development accounts only. |
| Privacy/operations — information officer and operations | Approve account data/retention, South Africa hosting and backup approach under DEC-007/015, and an operational account recovery/revocation procedure. Otherwise no real staff identities or production deployment. |

Open owner decisions to resolve during refinement: exact privileged roles and MFA method/recovery; who may invite and who may grant/revoke at each scope; whether any role may inherit descendants by default; maximum acceptable revocation/session window; initial administrative bootstrap and break-glass procedure; audit retention and who reviews privileged activity; treatment of dormant and shared staff accounts. Map decisions to the [decision register](../product/decision-register.md) or add IDs with named approvers before policy-dependent work is called done. `DEC-003/005/006` remain relevant to later member approval, household access and transfers; they are **not** assumed in this sprint.

## Explicitly not done

This sprint does not deliver member registration, `MemberUserLink`, member self-service login, giving history, payments, online checkout, messaging providers, private documents, pastoral/children's access, general organization administration, leadership assignment workflow, live data migration, production hosting or country rollout. Mozambique is next in the product direction, not part of this build; Eswatini and Zimbabwe remain unscheduled. The read-only organization slice is not a completed Church administration feature. Invitations may be modeled and tested without sending any real message. A green CI run or local SQL migration does not substitute for Church policy, legal/privacy or production release approval.
